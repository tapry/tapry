# CLAUDE.md — Tapry (formerly OpenTake)

Read `docs/plan/00-README.md` → `02-product-spec.md` → `03-recording-architecture.md` → `04-system-architecture.md` (plan v3, 1 Nov 2026), then `docs/decisions/`, before writing code. `10-design-inspiration.md` before UI, `12-ai-features.md` before AI work, `13-growth-features.md` before growth features, `14-riverside-parity.md` before adding any "Riverside has it" feature (check it isn't in Skip).

The product was renamed from OpenTake to **Tapry** (plan v3). New data is named `tapry`; the old name survives only as a fallback where data may already live under it, and those fallbacks must stay: localStorage is written as `tapry:<name>` and still read from `opentake:<name>` (`src/lib/client/stored.ts`); a browser that has the IndexedDB database `opentake-recorder` keeps using it (unsent chunks), others get `tapry-recorder`; recovery also honours the old Web Lock name `opentake:track:`; and `DATA_NAME` in the Compose `.env` (required, never defaulted) names the project, Postgres user/database and bucket: `tapry` from `setup.sh`, `opentake` on installs from before 0.4, including studio.tapry.app. The repo is github.com/tapry/tapry; images are at ghcr.io/tapry from the next release (0.2.0 and earlier stay at ghcr.io/mithrandiirr).

## What we're building
"The remote recording studio you own." A self-hostable, open-source remote recording studio: guests join by link in the browser; each participant is recorded locally at full quality, chunks are buffered in the browser (IndexedDB) and uploaded one object per chunk during the session (our storage or, later, the customer's own bucket); the host sees live per-guest upload status and quality alerts; a worker syncs and packages per-track files, a combined video and transcripts (speaker = track). AI runs on our/the customer's servers by default. Live call via LiveKit.

Priorities, in order: **1. never lose a recording · 2. simple guest flow · 3. privacy by default · 4. openness (exports, own storage)**. First paying customers: research teams, newsrooms, privacy-bound organisations; podcasters come through the free open-source version. v1 scope guard (plan v3): reliability + guest flow + transcripts + AI producer alerts + guest tech check + 2 free tools; everything else waits for paying users.

## Stack
TypeScript monorepo (pnpm + turborepo). Next.js (App Router), Tailwind, LiveKit (server + JS SDK), Postgres (PGlite in dev), S3-compatible storage (SeaweedFS for self-host and tests, R2 cloud, customer bucket later), ffmpeg worker, whisper.cpp for transcripts, Docker Compose, Caddy.

## Where the code deliberately differs from the plan
- **Chunks are stored in IndexedDB**, not OPFS: it works in every engine we test and gives atomic writes. OPFS can come later behind the same `ChunkStore` interface.
- **One storage object per chunk**, not S3 multipart parts: `docs/decisions/0001-one-object-per-chunk.md`.
- **Jobs live in Postgres** (`FOR UPDATE SKIP LOCKED`), not Redis + BullMQ: one less service to self-host.
- **Live status and quality alerts go through the server** (SSE + `/telemetry`), not the LiveKit data channel, so they work when the call doesn't.

Pages live under `/studios`; old `/shows` links redirect. Don't say "show" or "episode" in the product. Don't list webinars, live streaming or social clips as things it does: they aren't built (`docs/plan/14-riverside-parity.md`).
- The look is the "Tapry … Tembo" designs: zinc neutrals, terracotta accent, 6 px controls. The logo is `LogoMark` ("hanging tracks", brand colours, same in both themes; `apps/site` has its own with a `reversed` variant for terracotta backgrounds). Primitives in `src/components/ui.tsx` (Button sizes `sm`/`md`/`lg` and variant `link`: size by prop, class overrides of height and padding lose to the defaults), icons and the ember page frame in `ui-extra.tsx`, the dashboard frame in `app-frame.tsx`. The call stage and the full-screen view are dark in both themes and set their own `--ring`.
- Free tools on the website (`apps/site/src/app/tools/*-card.tsx`, each with its own page and FAQ through `ToolPage`): mic & camera test, upload-speed test, solo recorder (`/recorder`, in the tab's memory until saved, an hour at most), consent form generator (`/consent-form`) and recording data map (`/data-map`), both text built in the page with blanks in square brackets. All run in the browser; the privacy text says so.
- Everything on screen comes from real state: no placeholder people, numbers or meters. "Saved" means every track is complete; a stale health report (`STALE_REPORT_MS`) reads "Not reporting", never "up to date"; level bars move only while the call hears that person speak.

Cloud plans on the pricing page follow `docs/plan/06-monetization.md`. An offer that isn't built (Business: SSO, audit log) stays labelled planned either way.
- Dashboard pages across studios (`/recordings`, `/recordings/[id]`, `/studios/all`, `/guests`, `/transcripts`, `/storage`, `/settings`) read through `LibraryService` (`src/server/library.ts`) and `ProcessingService.listForOwner`: owner-scoped, read-only, no schema of their own. `/studios` still redirects to the newest studio. Transcript text is read from storage (4 MB cap, cached in memory) and never logged.
- Download links show friendly titles; the real file name is in `data-file-name` (tests read that).

## Sync
- Every timestamp a device sends is `localNow()` (`src/lib/client/clock.ts`: performance.timeOrigin + performance.now(), rounded) plus the green room's offset estimate. Never Date.now() for anything compared with the server: it jumps when the system clock is adjusted.
- Measured by `e2e/sync.spec.ts` (beeps on the real clock, skewed guest clock): ~1–5 ms between people, no drift over 60 min, nothing lost (Gate A: `E2E_SYNC_SECONDS=3600`). Device input latency (Bluetooth) isn't covered.

## Guest tech check
- `/join/<inviteCode>/check`: the host sends it before the session (studio page, under the invite link; the invite page links it too). Same secret as the invite, so a new invite link retires it. The green room's checks plus the camera, mic and headphones, a measured upload speed (throwaway bytes to `POST /api/check/:code/upload`, max 8 MB per request, live invite codes only) against what the studio sends (recording + call; slow is a warning, never a blocker), and a 5-s test recording played back locally (never uploaded).
- Results reach the host only when the guest presses Send (`POST /api/check/:code/report`: name, "Chrome on macOS", check codes and labels; no media). Table `tech_checks`, newest 50 per studio, 30 days shown, deleted with the studio.

## Admin health
- `/admin/health` (admins; `GET /api/admin/health` gives the JSON): `src/server/health.ts` checks the database (and pending migrations), storage (writes, heads and deletes `health/check-*.txt`), workers, job queue and failures (reasons only), transcripts, working space, the call (the server only reports whether it's set up; the page tests LiveKit from the admin's browser, since the server never talks to LiveKit and inside a container its public address often doesn't lead back) and the version.
- Workers are known from heartbeats: every JobRunner (`kind` inprocess or worker) upserts a `workers` row every 30 s with its version and `WorkerInfo` (ffmpeg/ffprobe version lines, whisper model found, free tmp space); gone after 3 missed beats; rows idle a day are removed. Ages are computed with the database's clock. The web server records its runner's first beat before serving.
- Update check only with `UPDATE_CHECK_REPO` (GitHub releases/latest, cached 6 h): privacy by default.

## Consent
- Each studio's `consentText` setting (empty: `defaultConsentText`, sound-only wording for audio-only studios); `consentTextFor` (packages/shared) gives the exact text. The invite page shows it and sends its SHA-256 (`consentHash`) with the join; the server works the text out itself and refuses a different hash (409 `consent_changed`: the host changed it meanwhile, the page reloads it).
- Kept once per distinct text in `consent_texts (hash, text)`; each guest has `participants.consent_hash` and `consented_at`. Never edit or delete a `consent_texts` row: records point at it.
- Consent record per recording (`GET …/recordings/:id/consent`, also last in the zip): everyone recorded in it, when each guest agreed, the hash, and each text in full. Guests who joined before texts were kept say so.

## Upload-speed check
- `POST /api/speed-test`: public, reads and drops up to 8 MB a request, 64 MB/min per address (last X-Forwarded-For entry, which Caddy sets), in memory (`src/server/speed-test.ts`). CORS only for `SPEED_TEST_ORIGINS`. The guest tech check uses its own invite-code endpoint with the same `drainBody`.
- `measureUpload` (`src/lib/client/tech-check.ts`): pieces from 256 KB doubling while under 0.75 s, first piece not counted, ~5 s, max 32 MB. The website's `/upload-speed-test` has a copy (and of the per-studio needs) and tests against `NEXT_PUBLIC_SPEED_TEST_URL`; unset, the page says it isn't connected and isn't linked.

## Guest end screen
- After the session, a guest sees their upload until it's done, then (`GuestAfterwards` in room.tsx) their own files from each recording once processed, from `GET /sessions/:id/my-recordings` (participant token; only their own audio/video outputs, never the combined video or anyone else's; signed links for 1 h, refreshed every 30 min). Studio setting `guestDownloads`, on by default.
- Recap email (`src/server/recap.ts`): the end screen offers "Email me a link" only when `SMTP_HOST` is set (any SMTP server, via nodemailer; encrypted unless `SMTP_INSECURE=true`; needs `SMTP_FROM` and `APP_URL`), and never unasked. `recap_requests` is its own queue, worked by every JobRunner: sent once every recording the guest is in has settled, retried 5 times. The address is removed once sent or given up on, and when the host deletes the recording. The link is `/recap/<token>`: only its hash is stored, it works 30 days, and a new request kills the old one (at most 3 sends per guest). Failures store the SMTP code only (`mailFailureReason`): nodemailer's messages quote the address.
- "Record your own, free" link only when `GUEST_PROMO_URL` is set (unset by default, so self-hosted installs don't advertise). E2E sets it to https://tapry.test/.

## Quality alerts
- Computed on each device (`src/lib/client/quality.ts`: mic peaks and RMS from the recorder's stream, the call's incoming sound for echo, upload lag, `storage.estimate`, visibility, recorder errors) and POSTed as codes to `/sessions/:id/telemetry` on change and every 3 s. Kept in memory in `LiveHub.health` and pushed in `SessionState.health`; stale after `STALE_REPORT_MS` (15 s). Metadata only: never audio, video or transcript text.
- Thresholds (tune with alpha users): clipping = more than 3 peaks ≥ −1 dBFS in 10 s; silent = below −55 dBFS for 30 s unmuted; too quiet = 5 s of talking in the last 30 s, none reaching −38 dBFS; echo = over 20 s with 5 s of the others talking, the mic's level follows the call's (correlation ≥ 0.6 at 0–300 ms, and stronger than with the mic leading by up to 600 ms, which is someone hearing their own voice back); upload behind = oldest unsent chunk over 60 s; low disk = under 1 GB of browser storage.
- Talking (voice activity) = RMS 12 dB above the noise floor (10th percentile of the last 15 s) and above −55 dBFS, carried 400 ms over word gaps. Talk balance: each device counts its own talking per recording and reports the milliseconds in telemetry; the host sees shares after 30 s of talking in all, and a nudge at 70% after 2 min.

## Processing
- Jobs live in Postgres (`jobs`, claimed with `FOR UPDATE SKIP LOCKED`). `WORKER=inprocess` (default, required with PGlite) runs them inside the web server; with Postgres, `src/worker-main.ts` (bundled to `dist-worker/worker.cjs`, the `worker` Compose service) runs them separately and the web server uses `WORKER=off`. Running jobs renew their lock; a stopped worker hands its job back; migrations take an advisory lock so web and workers can start together.
- A recording is processed once it is stopped and every track is complete; hosts can force it ("Process now").
- Processing timeline (`src/components/recording-timeline.tsx`): recorded → uploaded → files ready → transcript, from `recordings.uploaded_at` (set when the last track completes), `processing_started_at`, `processed_at`, `transcribed_at`, and `progress` (jsonb: stage collecting/rendering/saving/transcribing, done, total, current), which the runner writes as it goes (the pipeline's `onProgress` before each file) and clears when the job ends.
- All outputs are aligned to the recording start and cut to its exact length.
- One unreadable track never costs everyone their files: `renderRecording` skips it (`onSkipped`), the rest render, and the host sees who's missing (`recordings.skipped_tracks`) with Try again. Retention keeps the originals while any are skipped. Nothing readable at all fails the job as before.
- A track finishing while a render runs sets `recordings.rerun_requested` (under the recording's row lock, against the job finishing), and the job queues itself again. A transcript whose audio changed while it ran does the same.
- A track with a chunk missing from the middle (`hasGaps`) times its sound by timestamps, so the gap is silence and what follows stays in place. Whole tracks keep the sample-count timing the sync measurements were made with.
- Audio-only studios (studio setting `audioOnly`): no camera is asked for anywhere, so the call is voice only. When a recording has no video at all (audio-only, or every camera off), the combined output is `Combined.wav` (everyone mixed, levelled as a whole) instead of `Combined.mp4`. Not enforced on the server: switching a studio to audio-only affects who joins afterwards.
- Deleting (a recording, or a studio with all of its recordings) is soft for the rows and hard for the media: chunk and output rows go at once (usage drops), the recording/track rows stay with `deleted_at` so late uploads get **410 Gone**, and a `purge_recording` job deletes the stored files by prefix, then once more after presigned upload URLs have expired. Refused while recording or while a worker holds a job on it. Re-processing deletes the previous run's files.
- Loudness (studio setting `levelLoudness`, on by default): each person's WAV is measured (EBU R128 via loudnorm) and given one fixed gain toward -16 LUFS, capped by the -1 dBTP true-peak ceiling and +20 dB. No compression or limiting, so a peaky voice can land under -16. Their video's sound gets the same gain; the combined video's mix is levelled as a whole (mixed in float first).
- Zip download (`GET …/recordings/:id/zip`) is streamed by the web server from storage with client-zip: no stored zip, files stored uncompressed, exact Content-Length, ZIP64. It is the one download that passes through the web server; single files redirect to signed storage URLs.
- `RAW_RETENTION_DAYS` (off by default): a `purge_raw` job removes a recording's chunks after it's processed, only when processing is ready, every track complete and nothing queued; sets `recordings.raw_deleted_at`, after which re-processing is refused (409) and uploads get 410. Costs per recorded hour: docs/costs.md.
- Transcripts: a separate `transcribe_recording` job queued when processing succeeds. Each person's audio is transcribed alone (speaker = track), then merged by time into TXT/DOCX/SRT/VTT. DOCX (`toDocx`, apps/worker) is a minimal package written with our own stored-zip writer (`zip.ts`), no dependency. Off when `WHISPER_MODEL` is unset.
- Audio format (studio setting `audioFormat`, default wav): with flac, each finished WAV (per person, and the mix of a video-less recording) is converted to FLAC as the very last step, so alignment and loudness are identical; the WAV isn't kept.

## Video quality and 4K
- `VIDEO_TIERS` and `videoTier(quality, sourceHeight)` (packages/shared) are the one table of frame sizes and bitrates for the browser and the worker: 720p 4, 1080p 8, 1440p 14, 2160p 24 Mbit/s. Studio setting `videoQuality`: `720p`, `1080p`, `2160p`.
- 720p and 1080p studios behave as always (every person's video is that size, a test pins the ffmpeg arguments). `2160p` means **each camera's best, up to 4K**: the browser asks for 4K with `ideal` constraints and records at the bitrate of the tier the camera really delivers; the worker probes each person's pieces (`personVideoHeight`) and makes their file at that tier, never under 1080p and never upscaled. The combined video is always 1920×1080.
- Tapry Cloud: `Plan.video4k` (Studio, Team, Own storage, Business). `StudioService.check4k` refuses turning 4K on with 402 `plan_no_4k`; `sessionSettings` hands devices 1080p when the account no longer has 4K, without touching the studio's saved setting. Self-hosted: no limit.
- The call's copy still shrinks to 360p from a 4K camera (constraints on the clone, else the encoder's `scaleResolutionDownBy`). Verified in Chromium with its 4K fake camera; no real 4K camera has been tried, and storage figures for 4K in docs/costs.md are computed, not measured.

## Screen sharing
- A shared screen is track kind `screen` (shared `trackKind`, recorder `TrackKind`, DB check constraints on `tracks` and `outputs`): picture only, from `getDisplayMedia`, recorded by `RecordingController.setScreen` through the **main** upload queue. Unlike a mask it is a real part of the recording: counted in tracks and upload figures, waited for by processing, a file of its own, and in the guest's own files. Sharing again is a new track.
- Never reported through `onError`: a screen that can't be recorded leaves the camera and mic recording, and the room says so (`onScreenProblem`). `stallMs: 0`: a still screen encodes to nothing for a while.
- The call gets a **clone** of the screen track (`publishScreen` in call.ts, `Track.Source.ScreenShare`, 12 fps, 1.5 Mbit/s, `contentHint: "detail"`); the recorder's track is never constrained or stopped by the call. One sharer at a time (the button is disabled while a peer shares; not enforced by the server). Your own screen isn't shown back to you.
- Worker: a person's screen tracks always go the way of pieces (even one), in a 1920×1080 frame (`SCREEN_HEIGHT`). Each piece's last frame is held to the moment its last chunk ended (`endOffsetMs`) and black from there (`drawbox … enable='gte(t,end)'`), because a still screen sends few frames. No filters, no blur, no sound. Output kind `screen`, with `intervals` (seconds).
- Combined video: during each interval the screen is overlaid across the frame with the sharer's camera in the bottom-right corner (`PIP`); the grid is untouched outside them. A recording with a screen but no cameras still gets `Combined.mp4`.
- Tested: worker with real ffmpeg, server tests, and `e2e/screen.spec.ts` in Chromium (headless captures a dark screen). Not tried in Firefox or Safari.

## Solo links, producer, guide, markers, timeline exports
- **Solo link** (`studios.solo_code`, `solo_prompt`; `/solo/<code>`; `StudioService.soloJoin`): each visit is a session of its own in status `solo` (never the studio's one `open` live session) with one participant, role `guest`. `Participant.solo` (from the session's status, or a session with no host) lets that person start, stop and end it: `requireHost` accepts host **or** solo. The ticket carries `solo: { maxMinutes }`; the room then shows Record to them, opens no call, shows the prompt in the guide panel and stops at the limit (client-side; an abandoned one stays stopped/pending for the host to process or delete). 10 joins an hour per address, in memory.
- **Producer** (`participants.producer`, `PUT /sessions/:id/producer`, hosts only, not while they have a track in a running recording): the green room asks; their device never follows the recording, `createTrack` refuses with 409 `not_recorded`, and they are left out of "Not recording yet" and the recording card.
- **Guide** (`studios.guide`, `src/server/guide.ts`, `src/lib/guide.ts`): plain lines, `#` for sections. Never in settings or tickets: only `GET /sessions/:id/guide` for hosts (a solo person gets `solo_prompt` there instead, never the host's guide).
- **Markers** (`markers` table, `POST /sessions/:id/markers`, host or solo, only while recording, at most 500, timed by the server from the recording's start). Deleted with their recording.
- **Timeline exports** (`src/server/timeline-export.ts`): `Timeline.otio`, `.fcpxml`, `.rpp`, made on the spot from the outputs (per-person audio, video, screen; never the mix or "(original)") and markers, at the studio's frame rate; files referenced by name relative to the project, so they sit in the zip beside the media. Only OTIO has been loaded by a real library.
- **Frame rate** (studio setting `frameRate`, `FRAME_RATES`, `ffmpegFrameRate`): the worker's `rate(opts)` replaces the fixed 30 everywhere; left out, the ffmpeg arguments are exactly the old ones.

## After the recording: pauses, clips, share-safe transcripts
- **Pauses removed** (`keepRanges` in timeline-export.ts): speech intervals come from the captions' own times (`LibraryService.speech`); gaps under 2 s stay, 0.4 s of room is kept each side. `TimelineInput.keep` makes every generator emit one clip per kept part on every track (`segments()` in whole frames; REAPER to the millisecond with `SOFFS`). `GET …/timeline/<format>?pauses=out`; 409 `no_transcript` without captions. No rendering, nothing stored.
- **Clips** (`src/server/clips.ts`, table `clips`, job `clip_recording`, output kind `clip`): cut from the `combined` output with `-ss … -t …` and a re-encode (frame-exact); one job does all waiting clips. Deleted with their file, and all of a recording's clips go when it is processed again or deleted.
- **Share-safe transcript** (`src/server/redaction.ts`, `POST /api/recordings/:id/transcript/safe`, viewers allowed): `makeSafe` renames speakers (also where a name or its first word is said), masks emails, links, phone numbers (digit groups joined by one separator, 8+ digits, not dates) and listed terms as whole words in any script. `preview: true` returns counts only. Never stored, never logged. It changes text only: say so wherever it is offered.

## Roles, comments, activity, keeping time
- **Viewer** (`users.member_role`, `account_invites.role`, `User.viewer`): `asUser` refuses every non-GET from a viewer with 403 `viewer` unless the handler passes `{ viewers: true }` (leaving the account, comments, the share-safe download). A new write endpoint is closed to viewers by default; open it only if it changes nothing others rely on.
- **Comments** (`comments` table, `CommentsService` in collab.ts): anyone in the account, viewers too; deleted by the author or the owner, and with the recording.
- **Activity log** (`activity` table, ordered by `seq`): `asUser(fn, { log: "Deleted a recording" })` names the target before the handler runs (it may be gone after) and records only when the response is under 400. Names of things, never content; a year; the owner reads it (Settings, Members).
- **Studio keeping time** (setting `deleteAfterDays`): at processing, `keep_until` becomes the earlier of what it was and now + N days (never later; not on a rerun). `JobRunner.expire` now runs on every server, but without `TAPRY_CLOUD` it only deletes where the studio's setting is set today, so a date left by a plan is never acted on, and no warning emails go out.

## API keys, webhooks, share pages
- **API keys** (`src/server/integrations.ts`, `api_keys`, token `tpk_…`, hash only): `asUser` takes `Authorization: Bearer tpk_…` in place of the cookie. The key's `User` is a member of the account whose `id` is the key's (so never the owner; `user.apiKey`): anything that stores `user.id` as a user must write null for a key (comments, activity do). A key may GET everything a member can; a non-GET needs `{ keys: true }` on the handler, else 403 `not_for_keys`. New write endpoints are closed to keys by default. 300 requests a minute per key, in memory. `docs/api.md` lists what is open: keep it in step.
- **Webhooks** (`webhooks`, `webhook_deliveries`): `emitWebhook(tx, recordingId, "recording.ready" | "recording.transcribed")` in the job's own transaction builds the payload then (ids, names, times, file names and sizes: never media or text); `deliverWebhooks` runs each poll, signs with `Tapry-Signature: t=…,v1=HMAC-SHA256("<t>.<body>")`, retries 8 times up to 6 h apart. Addresses must be public https (`assertPublicEndpoint`), redirects are refused.
- **Share pages** (`src/server/share.ts`, `recordings.share_code`, `share_transcript`): `/share/<code>` and `/embed/<code>` are public, `noindex`, and play `GET /api/share/<code>/media` (302 to a signed link to the `combined` output). Off by default; a new link, switching off, or deleting the recording kills the code. The transcript is shown only when the host ticks it. `/embed/*` is the one path Caddy doesn't send `X-Frame-Options: DENY` for.
- **Calendar invite** (`src/lib/ics.ts`, `ScheduleInvite`): made in the browser, nothing stored.

## AI notes
- `src/server/notes.ts`. After a transcript is ready the runner queues `notes_recording` (only when the server has a notes model at all). The job reads `Transcript.txt` from storage, has one model write Markdown with fixed sections (summary, chapters, key points, quotes, show notes: `NOTES_INSTRUCTIONS`), appends a footer saying who wrote it, and saves `Notes.md` as an output of kind `notes`. `recordings.notes` (off/queued/processing/ready/failed) and `notes_error` (words from `NOTES_ERROR_TEXT`).
- **Which model, decided when the job runs** (`notesModelFor`): the local one whenever set (`OllamaNotes`, `AI_NOTES_LOCAL_URL` + `AI_NOTES_LOCAL_MODEL`; nobody opts in, nothing leaves); else the outside one (`AnthropicNotes`, `ANTHROPIC_API_KEY`, model `AI_NOTES_MODEL`, default `claude-opus-5-5`) **only if the recording's account owner allowed it** (`users.ai_outside_at`, Settings → Account, owner only) and, on Tapry Cloud, the plan has `aiNotes` (every paid plan); else no notes, and nothing is sent anywhere. Never send a transcript to the outside model on any other path.
- The Claude call goes through `@anthropic-ai/sdk` (`client.beta.messages.stream(...).finalMessage()`, `fallbacks: "default"` with beta `server-side-fallback-2026-07-01`); `stop_reason` `refusal` and `max_tokens` are failures with their own codes. Errors are kept by class and status only (`NotesError` codes): the SDK's messages can quote the request, and transcript text never reaches a log or the jobs table.
- Transcripts over `NOTES_MAX_CHARS` (600,000) get no notes rather than a cut one. Re-processing a recording deletes its notes with the other outputs; the new transcript queues new ones. `POST …/recordings/:id/notes` writes them again.
- Tested with fake models and a fake Ollama/Anthropic client. **No real model has written notes yet**: the prompt's quality is unjudged.

## Filters
- A person's choices (`trackFilters` in packages/shared: brightness 0–2, look none/warm/cool/mono, touchUp, noiseRemoval) never touch the recorder: it records the original camera and mic. They ride on each track (`tracks.filters`, sent at track creation; `PUT /sessions/:id/filters` updates the caller's tracks in recordings still running, and the client re-sends after a late registration), so they apply to a person's whole file.
- Live: with picture filters the call publishes a canvas drawn from **the call's clone** (`src/lib/client/filter-picture.ts`; the no-filter path is the plain clone as before); noise removal turns on the browser's `noiseSuppression` on the mic clone only, and is skipped where that would change the recorder's track. Browsers without canvas `filter` show no preview; files still get the filters. "Mirror my view" is local only.
- Files: the worker adds `eq` / `colortemperature` / `bilateral` **before** alignment (so late-start padding stays black) and `afftdn` with the track's own measured noise floor, its delay trimmed, before loudness is measured. One table (`BRIGHTNESS_VALUES`, `LOOK_VALUES`) feeds both the canvas and ffmpeg. No filters = exactly the old ffmpeg arguments (a test pins them). With noise removal the untouched audio is a second output, "… - audio (original)", never transcribed.
- `recordings.apply_filters` (Process again with/without filters, while originals are kept); a filtered render that fails is rendered as recorded and listed in `recordings.filters_failed`, which the host sees. Noise-removal settings were tuned on synthetic noise: tune with alpha users.
- Background blur (`background: "blur"`): the device segments the person on its own clone of the camera (`src/lib/client/person-mask.ts`: MediaPipe Tasks Vision, loaded on first use; its wasm is copied to `public/mediapipe` by `scripts/copy-mediapipe.mjs` before dev/build/e2e, the model is committed in `public/models`, both served by this server; sources and hashes in NOTICE.md). Live, the canvas draws the blurred frame, then the person through the mask; with no fresh mask the whole picture is blurred, never sharp.
- The mask is a third track, kind `mask` (256x144, ~15 fps nominal, picture only), recorded beside the camera with the same clock rules and uploaded through its own `UploadQueue`, so it never shows in upload figures, "all uploaded", alerts or the end screen. **A mask can only help**: masks are excluded from every count and list people see (`kind <> 'mask'`), never decide readiness (a mask still uploading gets `MASK_GRACE_MS` = 15 s, then files are made without it; a late mask re-renders through the late-track path), and a missing, unreadable or badly timed one (`MASK_MAX_GAP_MS` = 1 s; shorter uncovered time is blurred whole) means an unblurred file reported in `filters_failed`. The worker pairs a video only with the same person's nearest complete mask and blurs after alignment (`backgroundBlurGraph`: gblur + alphamerge + overlay; `scale2ref` is deprecated in ffmpeg 7 and will need replacing). Turned on mid-recording, blur is live only for that recording.
- Phase 3 (not built): background images, reusing the mask.

## Branding, usage, phones, guest languages
- **Branding** (`src/server/brand.ts`, table `studio_brands`, studio settings → Branding): an accent colour (`#rrggbb`) and a logo (PNG/JPEG/WebP by magic bytes, never SVG, 512 KB, base64 in the database) for the pages guests open: `GuestShell` takes `brand` (class `.branded` + `--brand`/`--brand-text` in globals.css recolour the accent and the backdrop; text colours stay ours), the share page shows the logo. Never the dashboard or the room. Logo served by `GET /api/brand/<studioId>/logo` (public, `nosniff`, CSP sandbox). Tapry Cloud: `Plan.branding` (Studio, Team, Business); a brand the plan no longer covers is kept and not shown, and can always be cleared.
- **Usage** (`LibraryService.usage`, `/usage`, `GET /api/usage`): existing recordings only, UTC months, counts never content.
- **Phones**: `keepAwake` (`src/lib/client/wake-lock.ts`) holds a screen wake lock while the session runs or anything is unsent, re-asked each time the page becomes visible; never a need. Stage buttons are `pointer-coarse:size-11`; fields are 16 px on coarse pointers (globals.css). Say "this device", not "this computer", in anything a guest reads.
- **Guest languages** (`src/lib/i18n`, `GUEST_LOCALES` in shared: en, fr, es, de, pt, ar): only the pages a guest opens. English (`messages/en.ts`) is the source; every language must have every key with the same `{places}` (test/i18n.test.ts). Server pages use `getT()` (cookie `tapry-lang`, else Accept-Language), client parts `useT()` under a `LocaleProvider`; with no provider it is English, which is how hosts' pages stay English (`SessionClient` gives a host "en"). **What a host receives stays English**: a `Check` has `label` (English, sent in tech-check reports) and `msg` (shown to the guest). Server errors are English; `errorText` shows our translation by error code where there is one. The default consent text is per language (`defaultConsentText(host, audioOnly, locale)`); the join sends `locale` and the server hashes that language's text. Not translated: page titles, the blur problem messages, the recap page (`/recap/<token>`), and anything only a host sees. Translations are unreviewed.
- **Research exports** (`toNvivo`, `toF4` in `src/server/redaction.ts`; formats `nvivo` and `maxqda` of `POST /api/recordings/:id/transcript/safe`): one entry per turn (same speaker, under 3 s apart). NVivo: `hh:mm:ss.t-hh:mm:ss.t<TAB>Speaker<TAB>Content`, CRLF, UTF-8 with a byte-order mark, no header. MAXQDA/ATLAS.ti: `Speaker: text #hh:mm:ss-t#` paragraphs (f4). Written from each program's documentation; never imported into the real program.
- **Profile pictures** (`src/server/avatars.ts`, `user_avatars`, `users.avatar_hash`, `User.avatarUrl`, `Avatar src`): each person sets their own (`PUT`/`DELETE /api/auth/avatar`, viewers too, never keys); PNG/JPEG/WebP by magic bytes, 256 KB; the settings page crops to a 256 px square first. Served by `GET /api/avatars/<userId>` (public: guests see the host's on the invite). Guests have none.

## Tapry Cloud (plans and billing)
- Everything here is off unless `TAPRY_CLOUD=true`: a self-hosted server has no plans, no limits, no Plan tab, and the billing endpoints answer 404 (a test pins this). Never put a limit in a path that runs without the flag. What is built and what isn't: `docs/cloud-billing.md`.
- `PLANS` (packages/shared) is the one table of hours, retention and badge, from `docs/plan/06-monetization.md`; change both together, and the website's pricing page (`apps/site`, its own copy).
- `BillingService` (`src/server/billing.ts`): hours are counted per recording, deleted ones included, per billing month (`billingPeriod`: calendar month on Free, the subscription's day of the month otherwise). The only refusal is before Record (`LiveService.beforeRecording` → 402 `hours_used_up`): **a running recording is never stopped and an upload is never refused over a plan**.
- Retention: `planRetention` sets `recordings.keep_until` when files are ready (first time only) and returns the originals' time for `purge_raw`; `JobRunner.expire` deletes past-due recordings through `deleteRecordingIn` (so never one recording or being processed). A bigger plan extends `keep_until` of what exists; a smaller one never shortens it.
- With email on, `warnExpiring` (run by `JobRunner.expire`) emails each host once about recordings within 3 days of `keep_until` and sets `expiry_warned_at`; deletion then needs that warning to be a day old. A failed email leaves it unset, so nothing is deleted unwarned. Extending `keep_until` clears it.
- A plan past `plan_ends_at` is Free (`effectivePlan`), with no job needed. Admins set plans by hand (refused when the account has a subscription).
- Website prices: `apps/site/src/content/tiers.ts` (Tier: name, plan, description, features, priceId month/year, listed). The page shows Paddle's `PricePreview` `formattedTotals.total` as returned (no maths, no re-formatting); `listed` shows only until it arrives. No country is passed: the site is static, so Paddle detects it from the IP. Paddle.js always loads Paddle Retain (ProfitWell) on live pages, with no switch: the legal page says so, and Paddle's script must stay off every other page.
- The Paddle environment is never defaulted: `BILLING_PADDLE_ENVIRONMENT` / `NEXT_PUBLIC_PADDLE_ENVIRONMENT` are required with a token and checked against its `live_`/`test_` prefix, or start-up and the site build fail.
- Checkout: with `BILLING_PADDLE_CLIENT_TOKEN`, `/checkout/<plan>` (owner only) loads Paddle.js (`@paddle/paddle-js`), there and on `/pay` only, and opens the one-page overlay (success: `/welcome`) with `customData.user_id` = the account id, which the webhook reads back. `BILLING_PRICES` maps price ids to plans (`:yearly` for the yearly price). Not yet run with a real token.
- Paddle webhooks (`src/server/paddle.ts`, `PaddleBilling.handleWebhook`): verified with the SDK's `webhooks.unmarshal` on the raw text (`req.text()`, never parsed first) and the signing secret, not the API key; bad signature 401, unreadable body 400, apply failure 5xx (Paddle retries; one transaction, so nothing half-applied). Handles subscription.created/updated/canceled, customer.created/updated, transaction.completed; others 200 "ignored". Applied once (`billing_events`, `paddle:<event id>`), upserted by Paddle id, older `updated_at` never overwrites newer.
- Mirror: `billing_customers`, `billing_subscriptions` (account_id from the checkout's `custom_data.user_id`, or linked later by transaction.completed). `syncAccount` sets `users.plan` to the biggest plan among subscriptions where `grantsAccess(status)` (active, trialing, past_due). **A scheduled cancel or pause never revokes access**; only status canceled/paused does. Subscriptions never set `plan_ends_at`. A plan set by hand (no subscription) is left alone.
- Portal: `POST /api/billing/portal` (owner, signed in) mints a session with the SDK for the customer found in our DB from the session's account, never from the request, and 303s to it; failures 303 back to the Plan tab with a code. Needs `BILLING_PADDLE_API_KEY`.
- **Never delete** the notification destination, products, prices, or any customer/subscription/transaction in Paddle or in the mirror tables to tidy up: they are the live fulfilment path.
- Lemon Squeezy webhook (`billing-webhooks.ts` → `BillingEvent` → `BillingService.apply`): signature first, applied once (`billing_events`), an older event never overwrites newer state. The log line says what was done, never whose. Not yet run against a live provider.
- Not built: extra hours and longer keeping as paid add-ons. Legal texts are drafts in `docs/legal-drafts.md`, not on the website.

## Waitlist and the website's sign-in state

All Paddle code stays. How to switch back: `docs/cloud-billing.md`.

## Accounts and members
- An account is its owner's `users` row; a member is a user whose `account_id` points at it. `User.accountId` is the account (own id for an owner). **Anything about studios, recordings, the plan or storage is looked up by `accountId`, never by `id`**; `id` is for who is signed in, their password and email links, and who hosts (`participants.user_id`, so two members can both be hosts of one session). A new owner-scoped query that uses `user.id` hides the account from its members.
- `MembersService` (`src/server/members.ts`): the owner invites by email; the link (token stored hashed in `account_invites`, 7 days, once) is always returned and also emailed where email is on. Accepting creates a log-in for the invited address even where sign-up is closed, already confirmed; a signed-in person with that address joins only if they have no studios or members of their own.
- Owner only (`requireAccountOwner`): inviting, removing, buying and the provider's portal, own storage. Members can leave; removing signs them out and leaves them an empty account of their own.
- Seats: `BillingService.seatsOf` (the plan's `seats` on Tapry Cloud, no limit elsewhere), counted with open invitations under a lock on the owner's row. A smaller plan removes nobody.

## Own storage
- An account's own S3-compatible bucket (`src/server/own-storage.ts`), on only with `STORAGE_SECRET_KEY` (secret keys are AES-256-GCM encrypted with it in `storage_targets`; never returned, never logged; changing the key makes them unreadable).
- **A session is bound to its storage when it opens** (`sessions.storage_target_id`, set in `openSession`, never changed). Replacing or removing a bucket retires the `storage_targets` row but keeps it, so older sessions still resolve. Never rebind a session.
- `RoutedStorage` wraps the server's storage in the web server and the worker: every key is `recordings/<session>/…` or `outputs/<session>/…`, so it finds the session's bucket from the key and no caller knows. A new kind of stored object must keep the session id as its second segment, or it lands in the server's storage.
- Setting up: `save` proves write, head and delete from the server (errors reported by name only), then the browser PUTs a signed test file exactly like a guest's upload and `confirmBrowserCheck` marks the target verified. Only a verified target is used: guests upload straight from browsers, and a bucket without CORS would stall their uploads.
- Endpoints must be public HTTPS (`assertPublicEndpoint`: no private, loopback or link-local addresses, by IP or by name) unless `OWN_STORAGE_ALLOW_PRIVATE=true`. Checked at save only; a hosted server should also block inward traffic at its firewall.
- Plans (`Plan.ownStorage`): "required" (Own storage plan: no session opens without a verified bucket, 409 `storage_not_set_up`), "allowed" (Business), "no". A self-hosted server offers it to every account.
- Verified against a second SeaweedFS as the "customer": browser preflight and PUT, upload, commit and deletion all in the customer's bucket. Not tried on Amazon S3, R2 or B2.

## Accounts by email
- `AccountService` (`src/server/account.ts`), on only when the server sends email (`SMTP_HOST`, `APP_URL`). Links are random tokens stored hashed in `account_tokens`, used once; a newer link of a kind replaces the older.
- New password: `/forgot` → email → `/reset/<token>` (1 h). The answer and its timing are the same whether or not the address has an account (the email isn't awaited); 3 an hour per account (dropped silently past that), 10 an hour per address (429). Setting it signs every device out and confirms the address.
- Confirming the address: required only where `TAPRY_CLOUD=true` and email is on (`verificationRequired`); then `createStudio` and `openStudio` refuse with 403 `email_unverified` and the dashboard shows `ConfirmEmailNotice`. The first account is confirmed by its setup code. `/verify/<token>` (3 days) confirms on a button press, never on page load: mail scanners open links.
- Failures are logged by SMTP code only (`mailFailureReason`); the address never reaches a log.
- Sign-up is limited to 5 an hour per address after the first account (`AuthService.countSignup`, in memory, attempts count).

## Limits on what a token may do
- Participant tokens don't expire (the end screen keeps using them), but uploads do: `UploadService.checkOpen` refuses tracks, chunks and completions `UPLOAD_GRACE_DAYS` (7) after Stop with 409 `recording_closed`, never 410, so a device keeps its chunks. A track's `startedAt` must be within clock slack of the recording. `MAX_TRACKS_PER_PERSON` (50) per recording; bytes per person capped at `BYTES_PER_SECOND_CAP` (48 Mbit/s, twice 4K's bitrate) × (length + 10 min); a completion's `lastSeq` may not run more than 10,000 past the last chunk.
- The first account needs `SETUP_TOKEN` when the server has one (`AuthService.checkSignup`, compared in constant time, checked before the password hash and again under the lock). `setup.sh` generates it; dev and tests set `SETUP_TOKEN` in the environment (e2e: playwright.config.ts).
- Logins are limited per email (10) and per address (50) per 15 min, in memory, idle entries dropped. The address is the last X-Forwarded-For entry, which Caddy sets from the PROXY protocol header the layer4 proxy adds (deploy/compose/Caddyfile): without that every visitor would be 127.0.0.1.
- Names (`plainText` in shared) reject control and format characters: the consent record is line-based.
- ffmpeg and ffprobe read raw uploads with `-format_whitelist` (`RAW_FORMATS`): only the WebM and MP4 demuxers see a guest's bytes.

## Recovery on the guest's device
- One tab per session (`holdSessionLock`, Web Lock `tapry:session:<id>`): a second tab waits and continues when the first closes, since two would record the person twice.
- A track keeps the token it was recorded under in its `meta` (`uploadToken` in `recording.ts`), so joining again as someone new doesn't strand it. The current ticket wins for the same person, because a host's token changes on reopening.
- `followSession` reconnects after 45 s without a byte (the server pings every 15 s), so a half-open connection can't make someone miss Record. The host sees "Not recording yet" after 20 s without a track.
- A recorder that stops by itself is restarted as a new track (up to 5 times; processing merges the pieces) unless the device is gone. No chunk for 15 s raises an alert, which clears when chunks return.

## Live call
- LiveKit, one room per session, identity = participant id. Optional: no `LIVEKIT_URL` → recording works without a call.
- The call publishes **clones** of the camera/mic tracks (scaled to 360p). Never publish, constrain or stop the tracks the recorder uses.
- Mute/camera-off disable the original tracks too: muted means silent in the recording as well.
- TURN: LiveKit's built-in relay at `turns:turn.<domain>:443`, routed by SNI in Caddy (caddy-l4). LiveKit and Caddy need `network_mode: host`; LiveKit excludes Docker bridge IPs for media. `?relay=1` on a session URL forces relay-only (for testing). Test: `e2e/turn.spec.ts` against a Linux host (see docs/dev-setup.md).
- No macOS LiveKit binaries exist; the dev build is compiled from source with a CGO-free CPU-stats patch: see `docs/dev-setup.md`.

## Rules
- **Never delete a local chunk until the server has confirmed it.** Data loss is the worst bug. The one exception: 410 Gone from the API (`TrackGoneError`) means the host deleted that recording, and the queue drops the whole track locally.
- Every chunk has seq number + server-time start; uploads are idempotent (re-uploading a part is safe).
- **Media, transcript text and personal data never appear in logs, telemetry or analytics**: metadata only.
- AI defaults to local; external AI only when the workspace allows it (when AI arrives).
- Don't build a full video editor or generative AI features (non-goals in `docs/plan/02-product-spec.md`).
- All features must work on self-hosted installs (cloud-only code goes behind flags or in `/ee`).
- Keep `packages/recorder` framework-agnostic and dependency-light.
- Add a regression test for every recording/sync bug found.
- Browser support claims must match the tested matrix in `docs/browser-support.md`.

## Backups
- `deploy/compose/backup.sh`: `pg_dump -Fc` of the database plus a copy of `.env` into `/var/backups/tapry` (700, root), kept only if `pg_restore --list` reads it back; older than `KEEP_DAYS` (14) removed, never the last one. It does not copy the media. Restore steps are in the script's header and docs/self-hosting.md.
- studio.tapry.app runs it nightly at 03:17 UTC from `/etc/cron.d/tapry-backup` (log: `/var/log/tapry-backup.log`). The script lives in the deployed code, so a deploy must keep `deploy/compose/backup.sh` in place. Those backups are on the server's own disk: off-server copies depend on the owner enabling Hetzner Backups or giving a destination.
